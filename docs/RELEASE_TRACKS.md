# Parallel legacy and optional-AI releases

## Release identities

|Track|Package version|GitHub tag|Source|
|---|---|---|---|
|Historical non-AI legacy|1.0.0|`v1.0.0-legacy`|Runtime base `29dd691bd339ead5e6bd080a976e2ee2f12c3d63`; preservation branch `legacy/non-ai`|
|Current deterministic core + optional AI|1.2.0rc13|`v1.2.0rc13`|Current release commit; exact SHA recorded in release manifest|

The legacy preservation commit changes only GitHub workflows and adds a release
note; runtime, tests, metadata and original CLI bytes remain unchanged. This is
necessary because the old `release: published` workflow would attempt a PyPI
upload even for a prerelease ([GitHub release-event guidance](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#release)). Only GitHub project assets are authorized.

No GitHub tags/releases existed at initial inspection. Legacy is therefore
published as a historical snapshot, not represented as a previously certified
stable release. Both are explicitly GitHub prereleases; old tags/assets are
never moved or replaced. No PyPI registry/account publication is performed.

The new version keeps one package with optional extras, avoiding two divergent
extraction engines. Core `unpacker` has only pefile/pyelftools dependencies;
AI contracts use `[ai]`, and selected providers use `[ai-openai]`, `[ai-claude]`
or `[ai-gemini]`. Installing an extra does not cause automatic cloud calls.
The old 1.0.0 source has no AI modules or CLI, and is not modified to retrofit them.

## Published downloads

* [Legacy historical prerelease](https://github.com/anpa1200/Unpacker/releases/tag/v1.0.0-legacy)
* [Optional-AI RC13 prerelease](https://github.com/anpa1200/Unpacker/releases/tag/v1.2.0rc13)

Each release has five assets: project wheel, sdist, release-manifest.json,
validation-summary.json and SHA256SUMS. All were downloaded and verified after
publication. Use the immutable tag, not an assumed package-index release.

```sh
gh release download v1.0.0-legacy --repo anpa1200/Unpacker --dir downloads/legacy
gh release download v1.2.0rc13 --repo anpa1200/Unpacker --dir downloads/ai
(cd downloads/legacy && sha256sum --check SHA256SUMS)
(cd downloads/ai && sha256sum --check SHA256SUMS)
```

The example uses GitHub CLI; the same five files can be downloaded through
the release page. Do not install a wheel before verifying its approved checksum.
See [exact test receipts and deployment status](RELEASE_STATUS.md).

## Install and keep both in parallel

Download the reviewed project wheel from the appropriate GitHub release and
verify its SHA256 against that release's `SHA256SUMS` and manifest. Asset names
are generated by Python packaging; the legacy wheel version stays 1.0.0 even
though its descriptive Git tag is `v1.0.0-legacy`.

```sh
python3.12 -m venv .venv-legacy
.venv-legacy/bin/python -m pip install /downloads/1200km_unpacker-1.0.0-py3-none-any.whl
.venv-legacy/bin/unpacker --help
.venv-legacy/bin/python -c 'import unpacker; print(unpacker.__version__)'

python3.12 -m venv .venv-ai
.venv-ai/bin/python -m pip install '/downloads/1200km_unpacker-1.2.0rc13-py3-none-any.whl[ai-openai]'
.venv-ai/bin/unpacker --version
.venv-ai/bin/unpacker-ai --help
```

Paths are operator-provided downloads, not bundled assets in the checkout.
Core-only modern use can omit the extra; offline preview needs `[ai]` but no SDK
or key. A single environment cannot contain both versions of the same package;
use the explicit executable paths above. Existing legacy environments are not
upgraded or edited automatically.

For controlled/offline deployments, use reviewed wheels and exact locks instead
of unconstrained resolution. Native emulation needs the separately reviewed
owned native wheel and applicable Windows resources; none is included in these
project-only release assets. The lock files retain their RC12 environment
provenance; installing the RC13 project wheel changes the project version,
not those external dependency hashes.

## Extraction and AI interpretation stay separate

For reviewed benign data, legacy retains its original CLI syntax:

```sh
.venv-legacy/bin/unpacker benign.bin -o legacy-output
```

The modern core supports strict evidence/acceptance controls:

```sh
.venv-ai/bin/unpacker benign-wrapper.bin -o new-output \
  --json --report-file new-report.json --require-accepted
```

Legacy does not have the newer sandbox, JSON, strict-acceptance or AI flags.
It retains historical limitations and lacks subsequent hardening. It is not a
safe production fallback merely because it is preserved alongside RC13.

With AI installed, default invocation is an **offline preview**:

```sh
.venv-ai/bin/unpacker-ai new-report.json --from-report
# Explicit equivalent:
.venv-ai/bin/unpacker-ai new-report.json --from-report --preview
```

No dotenv/key is read and no provider is constructed. Existing keys or
`--env-file` do not authorize sending. After inspecting and separately approving
the exact disclosure, the operator may intentionally request advice:

```sh
.venv-ai/bin/unpacker-ai new-report.json --from-report --send \
  --provider openai --model gpt-6.1-sol --env-file /secure/provider.env
```

This last command makes a real request and may incur provider charges; no such
call is included in release testing. `--preview --send` is rejected. RC12 AI
scripts that intentionally sent metadata must add `--send` when migrating;
otherwise they now receive preview JSON. Provider/account/model availability is
not guaranteed by the configured string. Never reuse a prior one-payload approval
as permission to transmit another private report.

AI sees only bounded allowlisted metadata, not specimen bytes, disassembly,
raw logs, paths or sample hashes. That metadata can still be sensitive. Advice
cannot run code, change extraction parameters or promote recovery. Non-AI
extraction never imports the AI/provider layer or silently falls back to it.

## Verification scope and artifact review

Release validation uses generated non-executable ELF/gzip data, fake providers
and mocked SDK responses. It checks both non-AI and AI workflows, core-only
installation, no mandatory cloud dependencies, explicit send/default preview,
package contents and installed/source behavior. Actual counts, checks, source
commit and asset hashes are recorded in the release validation manifest.
No paid provider calls, stored user credentials or unknown specimens are used.

The historical RC12 corpus remains **33 accepted, 9 partial, 4 timeout,
8 unsupported** across 54 fixtures/12 unique reference originals. It is not a
fresh RC13/legacy or VM corpus result. See [current status](CURRENT_STATUS.md).
The experimental VM has one benign core proof only. Host GDS is unresolved;
unknown samples, full VM worker acceptance and operational rollout remain blocked.

Release assets contain project Python/source, synthetic test definitions,
documentation and checksums. They exclude keys/.env, private machine evidence,
Windows DLL/LDLL, native dependency binaries, specimens, recovered programs,
wheelhouse caches and VM images. Project MIT licensing does not relicense
third-party components or waive Windows-resource rights.

## Upgrade and rollback

Keep the legacy environment and tag immutable. Install RC13 into a separate new
environment, verify the selected artifact and run approved benign checks before
changing an application launcher. Reverting an analyst workflow means selecting
the previous environment's explicit executable; do not downgrade in place or
force-move a tag. Neither environment becomes an accepted hostile-worker target
without its own containment, resource/license and operational gates.

Automated registry publishing stays disabled. These releases create no exposed
service, persistent runner, new credentials, host-security changes or deployment.
